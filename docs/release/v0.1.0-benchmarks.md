# v0.1.0 benchmark evidence

Platform: Apple M4 Pro, darwin/arm64, Go1.27.3. Workload: 10,000 normally
distributed 128-dimensional float32 items (seed99), 128 queries (seed1234),
ten trees, one build worker, build seed42, ten results, automatic searchK.
Build benchmarks use item seed42. Exact neighbor tests and C++ oracles run
separately; timing is not used to assert correctness.

```sh
go test -tags goannoy_scalar ./bench -run '^$' -bench '^BenchmarkAngularSearch$/^dim128$' -benchmem -count=5 -benchtime=1s
go test ./bench -run '^$' -bench '^BenchmarkAngularSearch$/^dim128$' -benchmem -count=5 -benchtime=1s
go test ./bench -run '^$' -bench '^BenchmarkAngularBuild$' -benchmem -count=5 -benchtime=300ms
go test ./bench -run TestSearchIntoAllocs -count=1
go test ./internal -run TestSingleMetricDoesNotLinkOtherEngines -v -count=1
```

The reviewed old branch measured scalar search36–46µs, accelerated22–24µs,
2,542B/search and103 allocations/search. Build used87.2MB and about43,372
allocations, taking178–186ms. These are historical same-host observations,
not a universal claim about Spotify Annoy or every dataset.

Initial new scalar measurements:22,259;21,421;20,586;20,366;20,473ns
(median20,586ns;57.2% of conservative36µs baseline). Accelerated:
8,110;7,513;7,533;7,579;9,700ns (median7,579ns;34.5% of22µs).
Both were0B/op,0allocs/op. Initial build median156.1ms and25.8MB/op,
about6,241 allocations; individual runs151.5,156.1,151.6,273.9,157.1ms.

Final repeated measurements:

| Mode | Five runs | Median | Ratio to conservative old baseline |
| --- | --- | --- | --- |
| Scalar search | 17,283; 17,309; 17,607; 18,521; 17,798 ns | 17,607 ns | 48.9% of 36µs |
| NEON search | 9,334; 8,210; 8,541; 8,367; 9,107 ns | 8,541 ns | 38.8% of 22µs |
| Scalar build | 157.18; 153.48; 148.66; 145.89; 194.89 ms | 153.48 ms | 86.2% of 178ms |

Both search modes: **0 B/op, 0 allocs/op**. Build: approximately 25.78MB/op,
6,241 allocations (first run 6,244), versus the old 87.2MB/op. A final scalar
run before loop-control unrolling measured 21,804ns (60.6% of baseline),
slightly missing the gate; preserving sequential accumulation while unrolling
four products lowered it to the result above. One explicitly discarded run
overlapped a fuzz run and measured 54–57µs early samples; it is not comparable.
Simultaneous compilation/other machine activity can inflate results.
The scalar target is <=60% and accelerated target <=75% of the conservative
reviewed baselines. Allocation is a blocking CI assertion; timing history is
non-blocking and records hardware/toolchain alongside every artifact.

## Footprint

Minimal consumer builds/searches one two-dimensional item and prints the result.
`TestSingleMetricDoesNotLinkOtherEngines` builds every metric separately,
checks symbols for absence of the other search engines, then rebuilds with
`-trimpath -ldflags='-s -w'` and reports file size.

| Metric | Stripped executable bytes (darwin/arm64) |
| --- | ---: |
| Angular | 1,739,650 |
| Dot | 1,739,650 |
| Euclidean | 1,739,650 |
| Manhattan | 1,739,650 |
| Hamming | 1,723,138 |

The old reviewed minimal consumer was about1,898,658bytes. Binary sizes
include the Go runtime and are workload/toolchain/platform-specific. All
runtime imports resolve to this module or the standard library; go.mod has
no external requirements. Sharing codec/storage code does not force unused
metric traversal into an application.
