# GoAnnoy v0.1.0 Design

**Status:** Approved, with the release target corrected from v1.0.0 to v0.1.0

**Date:** 2026-11-09

**Target module:** `github.com/mariotoffia/goannoy`

**Target release:** `v0.1.0`

## 1. Purpose

GoAnnoy v0.1.0 will be a Go-native implementation of Spotify Annoy that:

1. prioritizes ultra-high search and build performance;
2. remains easy to maintain;
3. has the smallest practical runtime and binary footprint;
4. stays true to Spotify Annoy's standard index formats and observable semantics;
5. feels designed for Go rather than translated from C++ or Python;
6. remains easy to extend without charging built-in metrics for extension points; and
7. has high-value, high-coverage automated tests.

The current branch contains useful fixes, but it does not yet satisfy those goals. v0.1.0 is therefore a deliberate pre-1.0 API break and architectural correction, not a promise to preserve the current public API.

## 2. Evidence and Review Coverage

The design is based on an adversarial review of every changed file on the branch:

- 69 changed files inspected;
- 42 production, build, and configuration files reviewed as code;
- 27 tests, fixtures, documentation, and assembly files reviewed manually;
- Spotify Annoy compared at commit `379f744667aba6b40ba3db8a07678df173a88f74`;
- cross-language files built and queried with both C++ Annoy and GoAnnoy;
- scalar and accelerated benchmarks captured on Apple M4 Pro;
- race, checkptr, vet, coverage, malformed-input, and cross-build probes run.

The review found that several branch fixes are correct, but also found format incompatibilities, unsafe memory access, incorrect algorithms, weak test oracles, and an API/storage architecture that cannot reach the stated performance and footprint goals without restructuring.

## 3. Release Contract

### 3.1 What v0.1.0 means

- The module remains `github.com/mariotoffia/goannoy`; there is no `/v1` suffix.
- The release may break all unreleased or pre-v0.1 APIs currently on the branch.
- The release does not promise Go API stability beyond its documented v0.1.0 surface.
- Subsequent pre-1.0 releases will document breaking changes and provide upgrade guidance.
- The standard Spotify Annoy file contract is independent of Go API stability and is treated as a compatibility requirement.

### 3.2 Supported standard format

v0.1.0 standard compatibility is defined as Spotify Annoy's normal combination:

- item identifier `S = int32`;
- scalar value `T = float32`;
- exact node layout and field ordering for the selected metric;
- little-endian hosts for direct mmap compatibility;
- metrics: angular, dot product, Euclidean, Manhattan, and Hamming.

GoAnnoy v0.1.0 will not advertise a standard-compatible float64 format. Nonstandard scalar or identifier widths require a future, explicitly versioned GoAnnoy format.

### 3.3 Compatibility levels

The project distinguishes these guarantees:

| Mode | Byte identity | C++ loads Go file | Go loads C++ file | Query semantics |
|---|---:|---:|---:|---:|
| Deterministic scalar build | Required against golden fixtures | Required | Required | Required |
| Parallel/fast build | Not required | Required | Required | Required within documented recall/tie rules |
| Loaded read-only search | N/A | N/A | Required | Required |
| Hamming | Required for deterministic fixture | Required | Required | Exact Hamming distance |

Tree topology may differ when parallel build ordering or floating-point reduction order differs. Such files must still be structurally valid, cross-loadable, and semantically correct.

Deterministic byte identity covers all defined node fields. Spotify leaves some
dot and Hamming split-node fields/padding uninitialized; tests canonicalize only
those unused bytes. GoAnnoy writes zero there. Angular, Euclidean, and Manhattan
fixtures additionally match the complete raw file bytes.

## 4. Public API

### 4.1 Package layout

Each built-in metric gets a concrete package:

- `github.com/mariotoffia/goannoy/angular`
- `github.com/mariotoffia/goannoy/dot`
- `github.com/mariotoffia/goannoy/euclidean`
- `github.com/mariotoffia/goannoy/manhattan`
- `github.com/mariotoffia/goannoy/hamming`

The root package contains only common value types, errors, workload profiles, and search constants. Public hot-path interfaces are removed. Applications may define the narrow interfaces they need around concrete GoAnnoy types.

### 4.2 Float-vector metric example

```go
builder, err := angular.NewBuilder(1536)
if err != nil {
    return err
}
builder.
    Trees(32).
    Workers(0).
    Seed(1).
    Profile(goannoy.Throughput).
    Capacity(expectedItems)

if err := builder.Add(id, vector); err != nil {
    return err
}

index, err := builder.Build(ctx)
if err != nil {
    return err
}
defer index.Close()

searcher := index.NewSearcher()
results := make([]goannoy.Result, 10)
n, err := searcher.SearchInto(query, results, goannoy.AutoSearchK)
```

The fluent builder is intentionally shallow: it configures resources and lifecycle policy, while metric selection is encoded by the package. Setters record a sticky configuration error that is returned by `Err`, `Add`, `Build`, or `BuildTo`; they never panic. This keeps chaining compact without hiding invalid configuration at execution time, avoids an invalid "builder without a metric" state, and keeps discoverability high.

### 4.3 Core public types

```go
package goannoy

type ItemID int32

type Result struct {
    ID       ItemID
    Distance float32
}

type SearchK int

const AutoSearchK SearchK = -1

type Profile uint8

const (
    Balanced Profile = iota
    Throughput
    LowMemory
)

type OpenOption uint8

const Prefault OpenOption = 1
```

Each float-vector metric package exposes concrete `Builder`, `Index`, and `Searcher` types with the same method names:

```go
func NewBuilder(dimension int) (*Builder, error)
func Open(path string, dimension int, options ...goannoy.OpenOption) (*Index, error)

func (b *Builder) Trees(int) *Builder
func (b *Builder) Workers(int) *Builder
func (b *Builder) Seed(uint64) *Builder
func (b *Builder) Profile(goannoy.Profile) *Builder
func (b *Builder) Capacity(int) *Builder
func (b *Builder) OnDisk(string) *Builder
func (b *Builder) Err() error
func (b *Builder) Add(id goannoy.ItemID, vector []float32) error
func (b *Builder) Build(context.Context) (*Index, error)
func (b *Builder) BuildTo(context.Context, string) (*Index, error)

func (i *Index) Dimension() int
func (i *Index) Items() int
func (i *Index) Trees() int
func (i *Index) VectorInto(goannoy.ItemID, []float32) error
func (i *Index) Vector(goannoy.ItemID) ([]float32, error)
func (i *Index) Distance(goannoy.ItemID, goannoy.ItemID) (float32, error)
func (i *Index) NewSearcher() *Searcher
func (i *Index) Close() error

func (s *Searcher) SearchInto(query []float32, dst []goannoy.Result, searchK goannoy.SearchK) (int, error)
func (s *Searcher) Search(query []float32, limit int, searchK goannoy.SearchK) ([]goannoy.Result, error)
func (s *Searcher) SearchByIDInto(id goannoy.ItemID, dst []goannoy.Result, searchK goannoy.SearchK) (int, error)
```

Dimensions are validated by `NewBuilder`. Fluent settings are validated immediately and retained as the builder's first sticky error. `Workers(0)` means runtime-derived parallelism; negative values are errors. `Trees`, `Capacity`, and dimensions must be positive when applicable.

### 4.4 Spotify operation mapping

The API preserves Spotify behavior without copying its Python/C++ surface literally:

| Spotify Annoy operation | GoAnnoy v0.1.0 operation |
|---|---|
| `add_item` | `Builder.Add` |
| `build(n_trees, n_jobs)` | `Builder.Trees(...).Workers(...).Build(ctx)` |
| `set_seed` | `Builder.Seed` |
| `on_disk_build` | `Builder.OnDisk` followed by `Build`/`BuildTo` |
| `save` | `Builder.BuildTo` |
| `load(prefault)` | metric package `Open(path, dimension, options...)` |
| `unload` | `Index.Close` |
| `get_n_items` | `Index.Items` |
| `get_n_trees` | `Index.Trees` |
| `get_item_vector` | `Index.VectorInto` or allocating `Index.Vector` |
| `get_distance` | `Index.Distance` |
| `get_nns_by_vector` | `Searcher.SearchInto` or allocating `Searcher.Search` |
| `get_nns_by_item` | `Searcher.SearchByIDInto` |
| `search_k == -1` | `goannoy.AutoSearchK` |
| `include_distances` | `Result` always carries the distance |
| `unbuild` | keep the separate `Builder`, add items, and build a new immutable snapshot |
| `verbose` | no library-global output; callers time/log operations themselves |

`Build` does not consume the builder. A successful build is an immutable snapshot; callers may add more items to the builder and build another snapshot. A failed build does not corrupt previously returned indexes.

As in Spotify Annoy, adding an existing ID replaces that item's vector and `Items` reports the addressable range `maxID+1`; sparse holes are not valid search-by-ID targets. Standard files are headerless, so `Open` requires the caller's dimension to compute and validate the node stride.

### 4.5 Hamming API

Spotify Annoy represents Hamming vectors as packed `uint64` words even though its language wrapper accepts bit-like values. The Go API makes the core representation explicit:

```go
builder, err := hamming.NewBuilder(bitDimension, options...)
err = builder.Add(id, packedWords)
n, err := searcher.SearchInto(packedQuery, dst, searchK)
```

The required word count is `(bitDimension + 63) / 64`. Unused high bits in the last word must be zero. Convenience bit-packing helpers may be provided outside the search hot path. Existing GoAnnoy Hamming files using one float per bit are not Spotify-compatible and must be rebuilt from source vectors.

Hamming exposes `VectorInto`/`Vector` with `[]uint64`; its remaining index and search operations match the float-vector packages.

### 4.6 Concurrency and ownership

- A built `Index` is immutable and safe for concurrent searches.
- A `Builder` is not safe for concurrent calls unless the documentation explicitly identifies a method as safe.
- A `Searcher` owns reusable scratch memory and is not safe for concurrent use.
- The recommended model is one `Searcher` per goroutine or worker.
- Closing an index while its searchers are in use is invalid and returns/documentedly causes a lifecycle error rather than an unsafe memory fault.
- Returned `Result` values never alias mmap storage.

## 5. Internal Architecture

### 5.1 Boundary validation, unchecked core

Public calls validate dimensions, identifiers, result capacities, lifecycle state, and `searchK` once. Files are fully validated on open. After those checks, internal search code operates on trusted, flat node bytes without repeated bounds or type checks.

This preserves safe Go behavior at public boundaries while allowing the inner loop to remain branch-light.

### 5.2 Metric-specialized engines

Common storage, heap, lifecycle, and configuration code lives under `internal/core`. Metric-specific codecs, distance kernels, split logic, and specialized search/build loops live under metric-specific internal packages.

Built-in metrics do not use interface dispatch inside node traversal. Specialization may be produced from checked-in generated source when it materially improves performance, but the generator and templates remain small, deterministic, and tested. A future experimental custom-metric package may use interfaces; importing built-in metrics must not include its cost.

### 5.3 Search algorithm

Each `Searcher` owns reusable buffers:

- a value-based candidate max/min heap as required by the traversal stage;
- candidate item IDs;
- distance/result pairs;
- query-node scratch bytes;
- deduplication and partial-selection scratch.

The search path:

1. validates the query and destination once;
2. grows scratch geometrically only when required;
3. traverses root nodes with a value heap;
4. collects candidate IDs without per-candidate allocation;
5. sorts and deduplicates IDs in reusable memory;
6. computes exact distances using one backend selected outside the loop;
7. maintains a bounded top-k max heap instead of sorting all results;
8. writes ordered results into the caller's slice.

After warm-up or explicit reserve, `SearchInto` must allocate zero bytes per operation for a stable workload.

### 5.4 Build algorithm

The builder owns all mutable construction state. Node representations are flat byte buffers with metric-specific typed accessors. Correctness comes first in the scalar deterministic builder; parallel construction is layered on the same codec and split invariants.

All five Spotify algorithms are required:

- angular split and distance;
- dot-product split including `dot_factor` propagation;
- Euclidean split and distance;
- Manhattan split and distance;
- Hamming random bit-coordinate split with brute-force fallback, packed storage, and popcount distance.

The random generator must match Spotify's algorithm where deterministic byte compatibility depends on it. Kiss64 remains the standard deterministic default; Kiss32 is retained only where compatibility/tests require it and uses multiplication in `698769069*z+c`, not addition.

### 5.5 Storage and lifecycle

- Standard indexes use exact metric codecs with layout assertions.
- `Open` validates file length, node stride, item count, roots, descendant counts, child IDs, and metric invariants before exposing an index.
- Empty and truncated files return typed errors.
- Opening a replacement file never destroys a currently usable index before the new file is validated.
- mmap and GC-backed allocators return errors; they do not panic on ordinary I/O or malformed data.
- `BuildTo` writes to a sibling temporary file, syncs, closes, and atomically replaces the destination where supported.
- `Close` is idempotent and reports meaningful unmap/close errors.
- On-disk build uses explicit lifecycle state and cleanup behavior.

## 6. Performance and Footprint

### 6.1 Workload profiles

Profiles choose resource strategy, not file semantics:

| Profile | Intent | Typical choices |
|---|---|---|
| `Balanced` | default | moderate scratch, stable backend, practical parallelism |
| `Throughput` | fastest repeated queries/build | eager reserve, more workers, accelerated kernel when available |
| `LowMemory` | smallest live memory | conservative growth, fewer workers, no speculative reserve |

Every individual setting remains overridable with explicit options. Profile selection must not change the standard file layout or distance definition.

### 6.2 Backend policy

- The scalar backend is portable, deterministic, and always available.
- Stable assembly backends may be selected once per search/build operation.
- Experimental Go SIMD is isolated behind an explicit build tag and pinned toolchain CI.
- Experimental SIMD is never required to build or use the library.
- Unsupported combinations fall back to scalar rather than failing compilation.

### 6.3 Footprint policy

- Core runtime packages use the standard library only.
- Profiling and development tools stay outside the runtime dependency graph.
- Importing one metric should not force all metric engines into the consumer binary.
- No global `GOEXPERIMENT` flags are required.
- Scratch capacity is proportional to the query candidate budget, not total index size.

### 6.4 Initial performance gates

Measured on pinned benchmark data and documented hardware/toolchain:

- warmed `SearchInto`: 0 allocs/op;
- scalar angular search: at most 60% of the current scalar ns/op baseline;
- accelerated angular search: at most 75% of the current accelerated ns/op baseline;
- build memory materially below the current ~87 MB/op baseline for the pinned 10k x 128 workload;
- no regression in recall or exact-distance ordering;
- stripped minimal consumer remains monitored per metric.

Performance thresholds are regression gates, not cross-machine absolute promises. CI records ratios against a pinned baseline where reliable; release evidence includes local benchmark output.

## 7. Error Model

The root package defines errors usable with `errors.Is`:

- `ErrInvalidDimension`
- `ErrInvalidVector`
- `ErrInvalidID`
- `ErrInvalidSearchK`
- `ErrInvalidOption`
- `ErrClosed`
- `ErrCorruptIndex`
- `ErrIncompatibleIndex`
- `ErrUnsupportedPlatform`

Errors wrap paths, metric names, offsets, or offending values where useful. Public operations do not panic for malformed files, invalid vectors, invalid IDs, nil contexts, empty data, or lifecycle mistakes. Programmer-only impossible-state panics may remain internal and must be protected by tests.

## 8. Testing and Verification

### 8.1 TDD discipline

Every behavior change follows red-green-refactor:

1. add the smallest test that fails for the intended reason;
2. run it and preserve the failure evidence;
3. implement the minimum fix;
4. rerun the focused test;
5. run the owning package and integration suites;
6. refactor only while green.

The initial red tests explicitly cover faults already demonstrated in the branch: malformed-vector unsafe access, split-node child overrun, dot-factor incompatibility, Hamming layout incompatibility, negative angular distance, Kiss32 mismatch, empty-file panic, and destructive reload.

### 8.2 Oracle hierarchy

Tests use independent oracles, in this order:

1. committed files built by pinned Spotify Annoy;
2. a pinned C++ compatibility harness exercised in CI;
3. mathematically direct reference implementations used only in tests;
4. differential randomized tests across scalar and accelerated backends;
5. property/fuzz tests for malformed storage and public boundaries.

Fixtures must never be silently skipped. A missing fixture is a test failure. GoAnnoy-generated output is not an independent oracle for GoAnnoy behavior.

### 8.3 Required suites

- exact codec/layout tests for all five metrics;
- C++ -> Go load/query compatibility;
- Go -> C++ load/query compatibility;
- deterministic scalar golden-byte tests;
- split-path tests large enough to exercise every metric's split implementation;
- invalid dimension, vector, ID, `searchK`, context, and lifecycle tests;
- corrupt, empty, truncated, and adversarial file tests;
- race and checkptr runs;
- fuzzing for file headers/nodes and public vector boundaries;
- scalar/assembly/SIMD differential tests;
- deterministic seeded recall tests;
- allocation and benchmark regression tests;
- cross-build tests for supported platforms and explicit experimental tags.

Coverage gates:

- at least 90% statement coverage for core and public packages;
- at least 85% overall statement coverage;
- every exported API has success, boundary, and error-path coverage;
- coverage numbers never substitute for independent compatibility oracles.

### 8.4 CI release matrix

The required release checks are:

```text
go test ./...
go test -race ./...
go test -gcflags=all=-d=checkptr=2 ./...
go vet ./...
go test -run Compatibility ./compat/...
go test -fuzz ... (time-bounded scheduled job)
GOARCH/GOOS cross-build matrix
experimental SIMD job on its pinned toolchain
benchmark/allocation regression job
```

## 10. Migration Skill

The repository includes `skills/goannoy-v01-upgrade/SKILL.md` for agents upgrading older source trees to v0.1.0. Because no reliable historical release version exists, the skill detects source shapes, including:

- `builder.Index[float32, uint32]` and other generic builder forms;
- `builder.Index()` convenience construction;
- direct `index.New` usage;
- context objects and batch search APIs;
- old metric, allocator, sorter, random, distance, and node interfaces;
- float64 standard-index attempts;
- legacy Hamming indexes.

The skill maps each shape to the metric package API, flags cases that cannot be automated, emits a migration report, and runs focused plus full verification. It must explicitly state that legacy Go Hamming files need rebuilding from original vectors; byte conversion without source semantics is not claimed safe.

## 11. Delivery and GitHub Workflow

Implementation work will use an ordered TDD plan and small, reviewable commits. The existing GitHub issue is linked to the new PR. The PR body contains the issue ledger above and updates each row to `Fixed`, `Deferred`, or `Not reproducible`, with evidence links or test names.

The PR remains draft until:

- every required compatibility fixture is independent and committed;
- safety, race, checkptr, vet, and normal tests are green;
- performance and allocation evidence is recorded;
- the migration skill is validated against representative legacy shapes;
- all ledger rows have an explicit disposition.

## 12. v0.1.0 Acceptance Criteria

The release is ready when:

1. all five Spotify metrics build, load, and search standard files cross-language;
2. deterministic scalar fixtures match expected bytes where specified;
3. public invalid inputs and corrupt files return errors without memory faults;
4. warmed `SearchInto` is allocation-free for stable workloads;
5. the documented performance and footprint gates pass or are revised with measured evidence before release;
6. the root/runtime dependency graph is standard-library-only;
7. the stable build works without experimental tags;
8. experimental acceleration is isolated and cannot break stable consumers;
9. core/public coverage is at least 90% and overall coverage at least 85%;
10. CI enforces normal, race, checkptr, vet, compatibility, cross-build, and allocation checks;
11. the upgrade skill produces an actionable report for representative earlier API shapes;
12. the PR issue table is complete and the linked issue is resolved or explicitly tracks deferred post-v0.1.0 work.
