# GoAnnoy v0.1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Use `superpowers:test-driven-development` for every production behavior change, `superpowers:systematic-debugging` for unexpected failures, and `superpowers:verification-before-completion` before commits, PR state changes, or completion claims.

**Goal:** Deliver GoAnnoy v0.1.0 as a safe, Go-native, small-footprint, high-performance implementation that reads and writes Spotify Annoy's standard files for all five built-in metrics.

**Architecture:** The root package contains only shared value types, errors, profiles, and constants. Concrete metric packages expose fluent builders, immutable indexes, and reusable searchers. Metric-specialized internal engines operate on validated flat node storage without hot-loop interfaces. Independent C++ fixtures define compatibility; public boundaries and file opening validate once so the inner loops can remain allocation-free and unchecked.

**Tech Stack:** Go 1.26+ stable language/toolchain, standard-library runtime, small checked-in generated Go where specialization is measured to help, platform assembly for stable acceleration, C++ only for compatibility fixture generation, GitHub Actions, and `gh` CLI for GitHub interaction.

**Spec:** `docs/superpowers/specs/2026-11-09-goannoy-v0.1.0-design.md`

## Global Constraints

- Target `v0.1.0`, not v1.0.0. Keep module path `github.com/mariotoffia/goannoy` without a major-version suffix.
- Breaking the current unreleased Go API is allowed. Breaking Spotify standard index compatibility is not.
- Standard format is `int32` item IDs and `float32` scalar vectors; Hamming storage is packed `uint64`.
- Follow red-green-refactor for every production change. Capture a focused failure before writing its fix.
- Never use a GoAnnoy-produced file as the sole oracle for GoAnnoy compatibility.
- Keep the stable build independent of experimental SIMD tags and toolchain experiments.
- Keep runtime packages standard-library-only. Development and command dependencies may remain separate only when justified.
- Do not add public hot-loop interfaces. Built-in metric selection happens through packages.
- Do not optimize past a failing correctness, race, checkptr, or compatibility test.
- Do not silently skip a missing fixture, unsupported backend, or unavailable compatibility check.
- Preserve unrelated user changes. Remove legacy packages only after replacements and migration guidance are green.
- Use `gh` for issue/PR operations. Keep the PR draft until the release matrix is green.
